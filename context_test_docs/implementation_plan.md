# RoboDawn 방식 Astra 에이전트: 구현 계획

작성일: 2026-10-06. 배경은 [robodawn_ideas.md](robodawn_ideas.md), 실험 조건은 [README.md](README.md)를 봅니다.

## 0. 고정 조건

| 항목 | 값 | 이유 |
|---|---|---|
| reasoning effort | `low` 고정. 옵션으로도 바꿀 수 없게 합니다. | 사용자 결정. high는 쓰지 않습니다. |
| 동시 시뮬레이터 | 1개 | 같은 서버에서 학습이 돌고 있음 |
| 시뮬레이터 우선순위 | `nice -n 10` | 학습을 방해하지 않기 위해 |
| 로봇 | PandaOmron (팔 1개, 바퀴 이동, 몸통) | |
| 과제 | PrepareCoffee, PanTransfer, OpenCabinet, PickPlaceSinkToCounter, StirVegetables | 사용자 고정 |
| 모델 호출 | `codex exec` (구독 로그인) | |
| 물체 위치 | 모델에게 주지 않습니다. 이미지와 로봇 자기 상태만 줍니다. | 논문과 같은 조건 |
| 성공 판정 | RoboCasa 내장 `_check_success` | 기준선과 같은 기준 |

reasoning을 low로 고정하면 모델이 깊게 생각하지 않습니다. 논문에서는 추론을 끄면 성공률이 47.0%에서 34.8%로 떨어졌습니다. 그래서 응답 형식에서 `scene`(장면) → `progress`(진행 상황) → `plan`(계획)을 먼저 쓰고 명령은 마지막에 쓰게 합니다. 생각을 출력 안에서 하도록 만드는 장치입니다.

## 1. 파일 구성

새 코드는 플러그인 안의 `astra_robodawn/` 하위 패키지 하나에 모읍니다. 기존 파일(`policy.py`, `run.py`)은 기준선으로 남겨 두고, `worker.py`에는 요청 종류 2개만 추가합니다.

```
plugins/inspect-robots-robocasa-astra/src/robocasa_astra/
├── worker.py              (수정) 요청 "command", "views" 추가. 실제 일은 astra_robodawn/executor.py, astra_robodawn/views.py가 함
├── policy.py, run.py      (기준선, 그대로) reasoning effort 옵션만 제거하고 low로 고정
└── astra_robodawn/
    ├── __init__.py
    ├── commands.py        명령 문법과 해석기 (RoboDawn core/commands.py 기반, 팔 1개 + 바퀴용으로 수정)
    ├── executor.py        [시뮬레이터 쪽] 명령 하나를 끝까지 실행하고 결과를 돌려줌 (OSC 반복 제어)
    ├── views.py           [시뮬레이터 쪽] 카메라 이미지에 격자, 손끝 표시, 축 표시를 그림
    ├── recorder.py        [시뮬레이터 쪽] 매 스텝 20fps MP4로 기록 (카메라 3대 가로 배치 + 현재 명령 자막)
    ├── codex.py           codex exec 호출: --json 사용량 수집, 용량 초과 시 재시도, 호출별 기록
    ├── prompts.py         고정 프롬프트(역할, 문법, 프로필, 시연)와 턴별 프롬프트, 응답 JSON 스키마
    ├── memory.py          메모장(모델이 씀) + 최근 12턴 기록 + 잡은 높이
    ├── loop.py            폐루프: 관측 → 호출 → 명령 실행 → 결과 → 다음 턴
    ├── cost.py            토큰 → API 환산 비용 (단가 표 1곳에서 관리)
    ├── run.py             실행 진입점 (CLI)
    ├── demo_builder.py    [오프라인] 전문가 시연(LeRobot) → 명령 순서 + 핵심 장면 이미지로 변환
    └── assets/
        ├── profile_panda_omron.yaml   로봇 설명서: 좌표계, 닿는 범위(실측), 카메라, 그리퍼, 팁
        └── demos/
            ├── primer/                명령 입문 (모든 과제 공통): demo.json + 이미지
            ├── OpenCabinet/           demo.json (출처 에피소드, 턴별 상태·계획·명령·효과) + frames/*.png
            ├── PickPlaceSinkToCounter/
            ├── PrepareCoffee/
            ├── PanTransfer/
            └── StirVegetables/

plugins/inspect-robots-robocasa-astra/tests/
├── test_commands.py       명령 해석과 크기 제한
├── test_prompts.py        프롬프트 조립 순서, 스키마
├── test_memory.py         메모장과 기록 요약
├── test_demo_builder.py   궤적 → 명령 변환 (구간 나누기, 명령 크기 제한)
└── test_cost.py           비용 계산

scripts/robocasa-astra/run_agent.sh      실행 스크립트 (.runtime/amp2.env 사용)
```

**역할 나누기:**
- 시뮬레이터 쪽(`executor`, `views`, `recorder`)은 워커 프로세스 안에서만 import합니다. robosuite가 필요하기 때문입니다.
- 호스트 쪽(`codex`, `prompts`, `memory`, `loop`)은 numpy와 PIL만 씁니다. 둘은 기존처럼 JSON 줄 단위로 통신합니다.
- 시뮬레이터를 별도 프로세스로 두면, 시뮬레이터가 죽어도 기록이 남고 `nice`도 그 프로세스에만 걸 수 있습니다.

## 2. 명령 문법

PandaOmron은 팔이 1개라서 `left`/`right`를 빼고, 바퀴 명령을 추가합니다.

**좌표계:** RoboTwin은 월드 좌표를 쓰지만, 주방마다 방향이 달라서 로봇 기준 방향 단어를 씁니다.
- forward: 로봇이 바라보는 방향
- left: 로봇의 왼쪽
- up: 위쪽

```
move forward|back|left|right|up|down <cm>   손끝을 로봇 기준 방향으로 이동, 방향은 유지. 1..20 cm
rotate roll|pitch|yaw <deg>                 손끝을 중심으로 회전. roll = forward축, pitch = left축, yaw = up축. |deg| <= 90
point down|forward|down45                   손끝 방향 프리셋 (아래 / 앞 수평 / 45도 아래)
gripper open|close|<0..1>                   그리퍼
base forward|back|left|right <cm>           바퀴 이동. 최대 50 cm
base turn <deg>                             제자리 회전. |deg| <= 45
home                                        팔을 처음 자세로
wait / done
```

- **명령 개수:** 한 턴에 1~4개입니다. 크기가 제한을 넘으면 잘라서 실행하고 결과에 "잘렸음"이라고 적습니다.
- **바퀴 명령:** 모든 과제에서 쓸 수 있습니다. 다만 프로필에 "목표가 팔이 닿는 범위 밖일 때만 쓸 것"이라고 적습니다. 사람 시연에서 바퀴를 쓴 과제는 StirVegetables뿐입니다(시연 30개 중 20개).

## 3. 실행기 (`executor.py`)

**제어 방식:** PandaOmron 팔은 OSC_POSE 컨트롤러이고, 로봇 기준 좌표로 한 스텝에 최대 0.05 m, 0.5 rad까지 움직입니다. 관측값 `robot0_base_to_eef_pos`와 `robot0_base_to_eef_quat`로 손끝 자세를 읽습니다.

**팔 명령 (move, rotate, point, home):**
1. 목표 손끝 자세를 계산합니다.
2. 매 스텝 남은 오차를 컨트롤러 입력(-1..1)으로 바꿔 넣습니다. 이때 바퀴 입력은 0, 모드는 팔 모드입니다.
3. 아래 중 하나가 되면 멈춥니다.
   - 위치 오차 1 cm 이하이고 각도 오차 5도 이하 (도달)
   - 10스텝 동안 진전이 없음 (막힘, 접촉 등)
   - 명령당 최대 60스텝

**그리퍼 명령:** 손가락이 멈출 때까지(최대 25스텝) 같은 명령을 유지한 뒤 열림 정도(0..1)를 읽습니다. 닫았는데 일정 값 이상에서 멈추면 "손가락 사이에 물체가 있음"이라고 알립니다.

**바퀴 명령:** 바퀴 모드로 속도 명령을 주고, 이동 거리와 회전각이 목표에 닿을 때까지(최대 80스텝) 반복합니다.

**결과로 돌려주는 것:**
- 성공/실패 여부
- 실제 이동 거리(cm)와 회전각
- 남은 오차
- 사용한 스텝 수
- 그리퍼 열림 정도와 메모
- 과제 성공 여부

실패할 때는 "팔이 움직이지 않았다" 또는 "일부만 움직였다"를 구분해서 알립니다(RoboDawn 방식).

**예산과 기록:**
- 실행에 쓴 시뮬레이터 스텝은 과제의 스텝 예산(1800 등)에서 차감합니다. 매 스텝 성공 여부를 확인해서, 성공하면 바로 끝냅니다.
- 매 스텝 영상 프레임을 `recorder`로 보냅니다. 프레임 파일(npy)은 저장하지 않고 바로 MP4로 씁니다. 지금 방식은 스텝당 약 0.6MB가 쌓이는데, 이 문제를 없애기 위해서입니다.

## 4. 이미지 (`views.py`)

| 이미지 | 크기 | 표시 |
|---|---|---|
| agentview_left | 384×384 | 작업면 격자(10 cm), 손끝 원과 수직선(작업면까지), 축 범례(forward 빨강, left 초록, up 파랑) |
| agentview_right | 384×384 | 같음 |
| eye_in_hand | 256×256 | 없음. 정렬 확인용 |

- **격자 위치:** 과제의 기준 설비(조리대, 싱크, 스토브 등) 윗면 높이에 로봇 기준으로 그립니다. 눈금은 로봇 기준 cm입니다(예: `F+40`, `L-20`).
- **투영:** 카메라 투영 행렬은 robosuite `camera_utils.get_camera_transform_matrix`로 구합니다.
- **위에서 보는 카메라:** RoboDawn의 top_camera에 해당합니다. 1차에서는 넣지 않습니다. OpenCabinet 시험 결과를 보고 위치 판단이 부족하면, 기존 카메라 위치를 옮겨서 추가합니다.

## 5. 프롬프트와 메모

**순서 원칙:** 매 턴 바뀌지 않는 부분을 앞에 둡니다. 앞부분이 같아야 캐시 할인($1/1M)을 받습니다.

```
[고정, 캐시 대상]
  역할 설명 → 명령 문법 → 로봇 프로필(YAML) → 명령 입문 → 과제 시연(1-shot일 때) → 응답 형식
[매 턴]
  TASK: <RoboCasa 지시문>  TURN n / 최대
  지난 명령 결과 (성공/실패, 실제 이동, 메모)
  현재 상태: 손끝 위치(로봇 기준 cm), 손끝 방향, 그리퍼 열림, 사용 스텝/예산, 잡은 높이
  메모장 + 최근 12턴 기록
  첨부 이미지 설명
```

**응답 형식:** `--output-schema`로 강제합니다. 그래서 JSON 형식이 깨지는 일은 생기지 않습니다.

```json
{"scene": "...", "progress": "...", "memory": "...", "plan": "...", "commands": ["move down 5", "gripper close"]}
```

**종료 조건:**
- 과제 성공
- 스텝 예산 소진
- 최대 턴 도달
- `done`을 성공 판정 없이 3번 연속 말함 (`done`만으로는 끝나지 않고 "아직 안 끝났다"고 알려줌)
- 모델 호출이 3번 연속 실패

## 6. Few-shot (시연) 설계

RoboDawn처럼 전문가 시연을 명령 순서로 바꿔서 넣습니다. 재료는 `/data/code/robocasa/datasets/v1.0`의 사람 시연(LeRobot 형식)입니다. 변환은 `demo_builder.py`가 오프라인으로 한 번 하고, 결과는 `assets/demos/<과제>/`에 저장해서 매 실행 똑같이 씁니다.

### 6.1 시연 고르기

| 과제 | 데이터 | 시연 주방 | 평가 주방(layout/style 1/1)과 겹침 |
|---|---|---|---|
| OpenCabinet | pretrain, 107개 | layout 11~60 | 없음 |
| PickPlaceSinkToCounter | pretrain, 108개 | layout 12~60 | 없음 |
| PrepareCoffee | pretrain, 102개 | layout 11~60 | 없음 |
| PanTransfer | target에만 있음, 510개 | layout 1~10 | 12개 겹침. 이 12개는 후보에서 뺍니다. |
| StirVegetables | pretrain, 105개 | layout 11~60 | 없음 |

과제마다 후보 시연 중 하나를 고릅니다. 기준은 아래와 같고, 고른 에피소드 번호와 이유를 `demo.json`에 적습니다.
- 길이가 중앙값에 가까울 것
- 그리퍼 사용 횟수가 전형적일 것
- 바퀴를 쓰지 않을 것 (StirVegetables는 가능하면)

### 6.2 궤적을 명령으로 바꾸기

시연의 상태값에는 로봇 기준 손끝 위치와 방향, 그리퍼 정보가 있습니다. 행동값에는 그리퍼 명령과 바퀴 모드가 있습니다. 변환 순서는 다음과 같습니다.

1. **구간 나누기:** 그리퍼를 열거나 닫는 순간과 바퀴로 움직이는 구간을 경계로 시연을 나눕니다.
2. **경유점 줄이기:** 각 구간에서 손끝 궤적을 몇 개의 경유점으로 줄입니다(허용 오차 2 cm, 방향 변화 10도 이상이면 새 점).
3. **명령으로 바꾸기:** 경유점 사이의 이동을 `move forward/left/up` 명령(1 cm 단위, 최대 20 cm)과 `rotate` 명령(5도 단위)으로 나눕니다. 그리퍼 경계는 `gripper open/close`, 바퀴 구간은 `base` 명령이 됩니다.
4. **턴으로 묶기:** 명령을 한 턴에 1~4개씩 묶습니다. 모델이 실제로 보낼 만한 형태로 만들기 위해서입니다.
5. **효과 적기:** 턴마다 그 명령이 실제로 만든 변화를 적습니다(예: "손끝이 손잡이 앞 2 cm까지 감", "그리퍼가 0.35에서 멈춤: 잡음").
6. **핵심 장면 이미지 고르기:** 시연 영상(agentview_left, 256px)에서 첫 장면, 그리퍼를 쓰는 턴마다, 마지막 장면을 뽑습니다. 과제당 최대 6장입니다.
7. **계획 문장 쓰기:** 턴별 `scene`/`plan` 문장은 제가 핵심 장면 이미지와 상태를 보고 씁니다. 논문은 이 부분을 VLM이 사후에 썼습니다. 숫자는 시연의 값을 그대로 쓰고, 맨 앞에 "전략을 따라 하고, 숫자는 자기 장면에서 읽으라"는 안내를 붙입니다.
8. **(가능하면) 검증:** 바꾼 명령 순서를 우리 실행기로 그 시연 장면(`model.xml.gz`, `ep_meta.json`)에서 재생해 봅니다. 성공하면 좋은 시연으로 확정하고, 실패하면 다른 시연을 고릅니다. 장면을 똑같이 복원할 수 없으면 이 단계는 건너뛰고, 건너뛰었다고 적습니다.

### 6.3 명령 입문 (`primer/`)

모든 과제에 공통으로 넣습니다. 깨끗한 장면에서 명령 하나하나의 효과를 보여주는 6~8단계입니다(이미지 포함).
- move: 위/앞/옆
- rotate yaw
- point down
- gripper close: 물체 없이 닫으면 0.0
- base forward
- 닿지 않는 곳으로 이동해서 "일부만 움직였다"는 실패 예시

평가 장면이 아닌 주방(layout 11 이상)에서 우리 실행기로 실제로 실행해 만듭니다.

### 6.4 실험 조건

- **0-shot:** 명령 입문만 넣습니다.
- **1-shot:** 명령 입문과 과제 시연 1개를 넣습니다. 본 실험은 1-shot입니다.

## 7. 과제별 설계

| 과제 | 스텝 예산 | 최대 턴 | 성공 조건 (RoboCasa) | 어려운 점 |
|---|---|---|---|---|
| OpenCabinet | 1050 | 30 | 모든 문 관절이 90% 이상 열림 | 손잡이를 정확히 잡아야 함. 호를 그리는 움직임. 양문이면 2번 |
| PickPlaceSinkToCounter | 900 | 30 | 물체가 용기 안 + 용기가 조리대 위 + 그리퍼가 물체에서 25 cm 이상 | 싱크가 깊어서 잡는 높이를 판단하기 어려움 |
| PrepareCoffee | 1800 | 45 | 머그가 토출구 아래 + 그리퍼가 머그에서 25 cm 이상 + 머신 켜짐 + 그리퍼가 버튼에서 15 cm 이상 | 단계가 4개. 수납장 안에서 옆으로 잡기 |
| PanTransfer | 1800 | 45 | 채소가 접시 위 + 팬이 화구 위 + 그리퍼가 팬에서 멀리 + 로봇이 채소를 한 번도 안 건드림 | 기울이기(회전). 채소를 건드리면 바로 실패 확정 |

- **판정 기준:** 각 과제의 성공 판정과 기준 거리(25 cm, 15 cm 등)는 RoboCasa 소스에서 확인한 값입니다. 프로필의 팁과 과제 시연에 "끝나면 물러나야 성공"이라고 적습니다. 논문의 실패 사례 (c)처럼, 모델이 끝났다고 판단해도 판정 기준과 어긋나는 경우를 막기 위해서입니다.
- **고정 장면:** 장면은 지금처럼 `--native-scene`, 첫 번째 layout과 style입니다. seed는 771001부터 씁니다.

## 10. 비용·시간 예상 (P4에서 실측해서 고침)

### 10.1 단가

Codex 사용량은 크레딧으로 차감됩니다. 출처는 OpenAI rate card이고, 캐시 쓰기는 Codex에서 과금하지 않습니다.

| 구분 | 1M 토큰당 크레딧 | API 환산 |
|---|---|---|
| 입력 | 250 | $10 |
| 캐시된 입력 | 25 | $1 |
| 출력 | 1,250 | $50 |

1 크레딧은 약 $0.04입니다.

### 10.2 턴당 토큰 (1-shot)

| 부분 | 토큰 | 근거 |
|---|---|---|
| Codex 기본 지침 | 약 7.5K (항상 캐시) | 실측 7,552 |
| 고정 부분: 문법·프로필·입문·시연 텍스트 | 약 7K | |
| 고정 부분: 입문 이미지 4장 + 시연 이미지 6장 | 약 9K | 256px 이미지 1장 약 0.9K (smoke 테스트에서 역산) |
| 매 턴 바뀌는 부분: 이미지 3장(384px 2장, 256px 1장) | 약 5K | |
| 매 턴 바뀌는 부분: 상태·결과·메모 | 약 1.5K | |
| 출력: JSON 응답 + low 추론 | 약 0.6K | |
| **합계** | **입력 약 30K, 출력 약 0.6K** | |

캐시가 되는 정도에 따라 턴당 비용이 달라집니다.

| 경우 | 캐시되는 입력 | 턴당 크레딧 | 턴당 API 환산 |
|---|---|---|---|
| 고정 부분까지 캐시됨 (기대) | 23.5K | 약 2.9 | 약 $0.12 |
| Codex 기본 지침만 캐시됨 (최악) | 7.5K | 약 6.5 | 약 $0.26 |

### 10.3 5개 과제를 1번씩 돌릴 때

5개 과제 모두 성공하지 못하고 최대 턴까지 간다고 가정한 최대치입니다. 최대 턴은 30 + 30 + 45 + 45 + 60 = 210턴입니다.

| 항목 | 캐시 잘 됨 | 캐시 안 됨 |
|---|---|---|
| 총 토큰 | 약 6.4M | 약 6.4M |
| 크레딧 | 약 620 | 약 1,370 |
| API 환산 | 약 $25 | 약 $55 |
| 걸리는 시간 | 약 1~1.5시간 | 같음 |

성공한 과제는 일찍 끝나므로 실제로는 이보다 적습니다.

### 10.4 Pro($200) 요금제에서 차지하는 비율

- **공식 한도:** Pro 200은 Codex에 5시간 한도가 없고 주간 사용량만 있습니다. 주간 크레딧 수치는 공식적으로 공개되지 않았습니다.
- **추정 한도:** OpenAI 커뮤니티의 한 사용자 추정치(Pro, 주당 약 5만~6만 크레딧)를 기준으로 계산했습니다.

| 경우 | 크레딧 | 주간 사용량 대비 |
|---|---|---|
| 5개 과제 1세트, 캐시 잘 됨 | 약 620 | 약 1% |
| 5개 과제 1세트, 캐시 안 됨 | 약 1,370 | 약 2.5% |
| 참고: 지금 방식(12차원 숫자 출력)으로 5개 과제 1세트 | 약 2,900 (약 2,000번 호출) | 약 5% |

추정 한도가 공식 값이 아니라서 이 비율은 대략적인 값입니다. P4(OpenCabinet 1번) 전후에 ChatGPT 설정의 사용량 화면에서 %를 직접 확인해서 이 표를 고칩니다.

## 11. 위험 요소

- **이미지 순서와 캐시:** `codex exec`가 이미지(`--image`)를 텍스트 앞에 넣으면, 매 턴 바뀌는 이미지 때문에 뒤의 고정 텍스트가 캐시되지 않을 수 있습니다. P3/P4에서 `cached_input_tokens`로 확인합니다. 캐시가 안 되면 `codex app-server`로 바꿔 입력 순서를 직접 정합니다.
- **실행기 수렴:** 제어 이득(gain)을 잘못 잡으면 OSC가 목표 근처에서 흔들리거나 접촉 중에 멈출 수 있습니다. P1에서 측정하고 조정합니다.
- **스텝 예산:** 명령 하나에 스텝을 많이 쓰면 턴이 남아도 스텝 예산이 먼저 바닥날 수 있습니다. P1 측정값으로 예산이 충분한지 확인합니다.
- **회전 조작:** 논문도 회전을 약점으로 꼽았습니다. PanTransfer와 OpenCabinet은 성공률이 낮을 수 있습니다.
